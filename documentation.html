معرفی و هدف پروژه

این پروژه یک سامانهٔ جست‌وجوی آگهی است که داده‌های ساختاریافته را از صفحات پویای سایت دیوار استخراج می‌کند، نتیجه را برای استفادهٔ مجدد در پایگاه داده نگه می‌دارد و از طریق یک API ساده به رابط کاربری React تحویل می‌دهد.

کاربر شهر، دسته‌بندی و در صورت نیاز حداقل و حداکثر قیمت را انتخاب می‌کند. backend ابتدا cache محلی را بررسی می‌کند؛ اگر داده‌ای برای زوج «شهر + دسته‌بندی» وجود نداشته باشد یا کاربر گزینهٔ «دریافت جدیدترین آگهی‌ها» را فعال کرده باشد، اسکرپر اجرا می‌شود. در پایان، نتایج مطابق بازهٔ قیمت فیلتر و به‌شکل JSON به فرانت‌اند ارسال می‌شوند.

فناوری‌های استفاده‌شده

پشتهٔ پروژه عمداً سبک انتخاب شده است: یک backend پایتونی، دیتابیس فایل‌محور و یک SPA مبتنی بر React و TypeScript.

Backend

Python 3

زبان اجرای API، اسکرپر و منطق دسترسی به داده.

FastAPI

تعریف endpoint، اعتبارسنجی query parameterها، CORS و مستندات خودکار Swagger.

Playwright

باز کردن Chromium، اجرای JavaScript صفحهٔ دیوار و خواندن عناصر آگهی.

SQLite

ذخیرهٔ محلی و cache کردن آگهی‌ها بدون نیاز به سرویس دیتابیس جداگانه.

Regex + Logging

پاک‌سازی قیمت و ثبت رخدادهای اجرای backend.

Frontend

React 19 + TypeScript

پیاده‌سازی رابط کاربری component-based و مدل نوعی آگهی.

Vite

اجرای محیط توسعه، build و تزریق متغیر VITE_BASE_URL.

React Query v3

مدیریت وضعیت درخواست دستی با useMutation، شامل data و isLoading.

Axios

ساخت درخواست HTTP، تبدیل پارامترها به query string و مدیریت response/error interceptor.

React Router

ارائهٔ صفحهٔ اصلی در مسیر / با lazy loading.

توابع اصلی backend و نقش هرکدام

فراخوانی اسکرپر مستقیماً در تابع endpoint انجام می‌شود. فهرست زیر تمام توابع مؤثر در این زنجیره را از اتصال دیتابیس تا استخراج قیمت نشان می‌دهد.

get_connection()database.py

با sqlite3.connect("ads.db") یک اتصال تازه می‌سازد. هر درخواست API اتصال خودش را باز و در پایان می‌بندد.

startup()main.py

در شروع FastAPI اجرا می‌شود و جدول ads را در صورت نبودن می‌سازد؛ سپس commit و close انجام می‌دهد.

get_ads(...)main.py

handler مربوط به GET /ads است: cache را بررسی می‌کند، در صورت نیاز scrape_divar را صدا می‌زند، رکوردها را ذخیره و پاسخ را serialize می‌کند.

scrape_divar(...)scraper.py

URL دیوار را می‌سازد، Chromium headless را بالا می‌آورد، حداکثر ۲۰ آگهی معتبر را جمع می‌کند و یک list از dictionaryها برمی‌گرداند.

extract_price_number(ad)scraper.py

متن‌های توضیح کارت را می‌خواند، فقط موارد دارای «تومان» را نگه می‌دارد و بیشترین قیمت عددی معتبر را برمی‌گرداند.

fa_to_en(text)scraper.py

ارقام فارسی ۰…۹ را پیش از اجرای regex به ارقام انگلیسی تبدیل می‌کند.

محل واقعی فراخوانی اسکرپر

عدد 20 همان limit اسکرپر است و از query parameter دریافت نمی‌شود؛ در نتیجه هر بار refresh حداکثر ۲۰ آگهی قیمت‌دار جمع‌آوری می‌کند.

اسکرپر چگونه داده را جمع می‌کند؟

Playwright به‌جای دریافت HTML خام، یک مرورگر واقعی headless اجرا می‌کند تا محتوای JavaScript-driven سایت دیوار قبل از استخراج آماده شده باشد.

  1. ساخت URL

    آدرس از الگوی https://divar.ir/s/{city}/{category}?price={min}-{max} ساخته می‌شود.

  2. راه‌اندازی Chromium

    مرورگر با حالت headless و آرگومان‌های کاهش تشخیص automation اجرا می‌شود.

  3. ساخت browser context

    User-Agent دسکتاپ، viewport برابر ۱۹۲۰×۱۰۸۰ و locale فارسی تنظیم می‌شود.

  4. بارگذاری صفحه

    ابتدا networkidle امتحان می‌شود و در صورت خطا، بارگذاری با domcontentloaded تکرار می‌شود.

  5. انتظار برای محتوا

    پس از ۵ ثانیه، selector مربوط به article.kt-post-card تا سه مرتبه بررسی می‌شود.

  6. استخراج فیلدها

    عنوان، قیمت، href آگهی و src تصویر از selectorهای اختصاصی کارت خوانده می‌شوند.

  7. حذف دادهٔ نامعتبر

    آگهی بدون قیمت عددی کنار گذاشته می‌شود؛ نبود عنوان با «بدون عنوان» و نبود لینک/تصویر با رشتهٔ خالی جبران می‌شود.

  8. خاتمهٔ امن

    در بلوک finally مرورگر بسته می‌شود و list نتایج حتی در صورت خطا برگردانده می‌شود.

نحوهٔ ذخیره‌سازی در SQLite

فایل ads.db هم مخزن داده و هم cache پروژه است. جدول در رویداد startup ساخته می‌شود و لینک آگهی مانع ثبت دادهٔ تکراری است.

ستون نوع نقش قید
id INTEGER شناسهٔ داخلی رکورد Primary Key / Auto Increment
title TEXT عنوان آگهی —
price_number INTEGER قیمت نرمال‌شده برای مقایسهٔ عددی —
city TEXT slug شهر انتخاب‌شده —
category TEXT slug دسته‌بندی —
link TEXT آدرس کامل آگهی UNIQUE
image_url TEXT آدرس تصویر —

درج آگهی‌ها

backend/main.py
for item in new_data:
    cursor.execute("""
        INSERT OR IGNORE INTO ads
        (title, price_number, city, category, link, image_url)
        VALUES (?,?,?,?,?,?)
    """, (
        item["title"], item["price_number"], city,
        category, item["link"], item["image_url"]
    ))

conn.commit()

پارامترگذاری با ? از چسباندن مستقیم ورودی کاربر به SQL جلوگیری می‌کند. INSERT OR IGNORE نیز در صورت تکراری بودن link خطا تولید نمی‌کند و رکورد جدید را نادیده می‌گیرد.

خواندن و فیلتر نهایی

query پایه بر اساس شهر و دسته‌بندی ساخته می‌شود. اگر min_price یا max_price ارائه شده باشند، شرط‌های >= و <= به SQL افزوده می‌شوند. هیچ ORDER BY یا pagination در نسخهٔ فعلی وجود ندارد.

قرارداد API و endpointهای استفاده‌شده

تنها endpoint کاربردی این پروژه برای صفحهٔ فعلی GET /ads است. مستندات تعاملی FastAPI نیز به‌صورت خودکار در /docs ارائه می‌شود.

پارامتر نوع الزامی توضیح
city string بله slug شهر؛ مانند tehran
category string بله slug دسته‌بندی؛ مانند mobile-phones
min_price integer خیر حداقل قیمت به تومان
max_price integer خیر حداکثر قیمت به تومان
force boolean خیر پیش‌فرض false؛ با true cache قبلی حذف و اسکرپر اجرا می‌شود

نمونهٔ درخواست

GET http://127.0.0.1:8000/ads
    ?city=tehran
    &category=mobile-phones
    &min_price=10000000
    &max_price=60000000
    &force=false

نمونهٔ پاسخ

[
  {
    "title": "گوشی موبایل ...",
    "price": 25000000,
    "link": "https://divar.ir/v/...",
    "image_url": "https://..."

backend هنگام ساخت پاسخ، نام داخلی price_number را به price تبدیل می‌کند؛ بنابراین interface فرانت‌اند با نام IAd.price هم‌خوان است. نبود پارامترهای اجباری یا ارسال مقدار غیرعددی برای قیمت باعث پاسخ validation با وضعیت 422 از FastAPI می‌شود.

جریان کامل داده؛ از کلیک کاربر تا نمایش نتیجه

زنجیرهٔ زیر ترتیب دقیق فراخوانی‌ها را میان componentها، سرویس HTTP، endpoint، دیتابیس و اسکرپر نشان می‌دهد.

  1. تکمیل فرم

    کاربر دسته‌بندی، شهر، بازهٔ قیمت و وضعیت refresh را در SearchForm تعیین می‌کند.

  2. اعتبارسنجی

    useForm.validateForm() وجود شهر و دسته‌بندی را کنترل می‌کند؛ قیمت‌ها اختیاری‌اند.

  3. پاک‌سازی payload

    cleanObject رشته‌های خالی را حذف می‌کند. مقدار boolean برابر false حذف نمی‌شود.

  4. شروع mutation

    mutate(params) از hook مربوط به useIndexAds فراخوانی می‌شود.

  5. ارسال GET

    fetchService آدرس پایه را با /ads ترکیب و پارامترها را از طریق Axios به query string تبدیل می‌کند.

  6. تصمیم cache-first

    get_ads تعداد رکوردهای شهر و دسته‌بندی را می‌شمارد و مسیر cache یا scraper را انتخاب می‌کند.

  7. ذخیره و query نهایی

    در مسیر scrape، داده‌ها با INSERT OR IGNORE ثبت می‌شوند؛ سپس فیلتر قیمت روی SQLite اعمال می‌شود.

  8. serialize پاسخ

    FastAPI آرایه‌ای شامل title، price، link و image_url برمی‌گرداند.

  9. به‌روزرسانی UI

    React Query مقدار data را به‌روز می‌کند و AdsResult برای هر عنصر یک کارت می‌سازد.

  10. هدایت دید کاربر

    اگر حداقل یک نتیجه موجود باشد، scrollIntoView صفحه را با حرکت نرم به بخش نتایج می‌برد.

فراخوانی API در فرانت‌اند

فرانت‌اند درخواست جست‌وجو را به‌عنوان یک عمل دستی مدل می‌کند؛ درخواست تنها بعد از submit فرم اجرا می‌شود، نه هنگام mount صفحه.

۱. سرویس feature

src/features/home/services/useLanding.ts 
const useIndexAds = () => {
  return useMutation((params?: any) =>
    fetchService("GET", "/ads", { params })
  );
};

۲. اتصال فرم به mutation

src/features/home/index.tsx
const { mutate, isLoading, data } = useLanding().useIndexAds();

const handleSearchForm = (formData: any) => {
  mutate(cleanObject({ ...formData }));
};

۳. ساخت URL نهایی

مقدار baseUrl از فایل محیطی خوانده می‌شود: VITE_BASE_URL=http://127.0.0.1:8000. تابع fetchService متد را اعتبارسنجی، route را normalize و سپس Axios را با params فراخوانی می‌کند. در نتیجه مرورگر endpoint را با query string صدا می‌زند.

Interceptorها

  • درخواست‌ها headerهای عمومی Accept و در صورت وجود token، Authorization دریافت می‌کنند.
  • خطاهای شبکه و statusهای ۴۰۰، ۴۰۱، ۴۰۳، ۴۰۴ با toast فارسی به کاربر اعلام می‌شوند.
  • خطاهای سمت سرور با status حداقل ۵۰۰ تا سه مرتبه و با فاصلهٔ یک ثانیه تکرار می‌شوند.
  • در سطح QueryClient، refetch هنگام focus غیرفعال و retry مربوط به queryها صفر است.

داده چگونه در فرانت نمایش داده می‌شود؟

interface نوعی IAd دقیقاً چهار فیلد پاسخ API را تعریف می‌کند و component AdsResult سه حالت «قبل از درخواست»، «نتیجه‌دار» و «بدون نتیجه» را پوشش می‌دهد. 

export interface IAd {
  image_url: string;
  link: string;
  price: number;
  title: string;
}

اگر data برابر undefined باشد، component هیچ خروجی‌ای render نمی‌کند.

هنگام ارسال فرم

متن دکمه با LoadingDot جایگزین و pointer event دکمه غیرفعال می‌شود.

پاسخ دارای داده

آگهی‌ها با map داخل grid چندستونه به کارت تبدیل می‌شوند.

آرایهٔ خالی

پیام «آگهی مورد نظر یافت نشد!» در بخش نتایج نمایش داده می‌شود.

اجزای هر کارت آگهی

  • تصویر: ImageLazy پس از رخداد load، opacity را از صفر به یک می‌رساند؛ اگر URL خالی باشد تصویری render نمی‌شود.
  • عنوان: متن در دو خط clamp می‌شود تا ارتفاع کارت‌ها کنترل شود.
  • قیمت: تابع numberSeparate جداکنندهٔ هزارگان را اضافه و سپس «تومان» را نمایش می‌دهد.
  • لینک: با کلیک روی «مشاهده آگهی»، window.open(link, "_blank") صفحهٔ اصلی آگهی در tab جدید باز می‌شود.

مدیریت وضعیت‌ها و خطاها

کنترل خطا میان scraper، FastAPI و Axios تقسیم شده است، اما رفتار هر لایه یکسان نیست.

لایه رفتار فعلی خروجی قابل مشاهده
Scraper exception را catch، traceback را چاپ و مرورگر را می‌بندد ممکن است list خالی یا ناقص برگردد
FastAPI validation نوع و وجود query parameterها را بررسی می‌کند پاسخ 422 برای ورودی نامعتبر
Axios interceptor خطاهای HTTP را دسته‌بندی و برای 5xx retry می‌کند toast فارسی
React component isLoading و data را مصرف می‌کند loader، grid نتیجه یا empty state

چون scrape_divar خطا را دوباره raise نمی‌کند، شکست کامل scraping می‌تواند در لایهٔ API به پاسخ موفق 200 با آرایهٔ خالی تبدیل شود؛ بنابراین در نسخهٔ فعلی فرانت نمی‌تواند «نتیجه‌ای نیست» را از «اسکرپر شکست خورد» تفکیک کند.

ساختار فایل‌های اصلی پروژه

backend کوچک و لایه‌ای است؛ فرانت‌اند از ساختار feature-based استفاده می‌کند تا component، service، type و style مرتبط با صفحهٔ خانه کنار یکدیگر بمانند.

backend باید از پوشهٔ backend اجرا شود تا مسیر نسبی ads.db به همان فایل مورد انتظار اشاره کند. سپس فرانت‌اند با Vite بالا می‌آید.

Backend

cd backend
pip install fastapi uvicorn playwright
playwright install chromium
python -m uvicorn main:app --reload

Frontend

cd frontend/divar-scrap
npm install
npm run dev

آدرس‌های قابل استفاده

سرویس آدرس کاربرد
Frontend http://localhost:5173 فرم جست‌وجو و نمایش آگهی‌ها
API http://127.0.0.1:8000/ads دریافت نتایج JSON
Swagger http://127.0.0.1:8000/docs آزمایش تعاملی endpoint
پیش‌نیاز ارتباط فرانت و backend فایل frontend/divar-scrap/.env باید مقدار VITE_BASE_URL=http://127.0.0.1:8000 داشته باشد.

جمع‌بندی

هستهٔ پروژه یک pipeline روشن دارد: فرم React پارامترهای جست‌وجو را می‌سازد؛ GET /ads میان cache و scraping تصمیم می‌گیرد؛ Playwright دادهٔ خام صفحه را به رکورد ساختاریافته تبدیل می‌کند؛ SQLite نتیجه را نگه می‌دارد؛ و AdsResult پاسخ JSON را به کارت‌های قابل مشاهده تبدیل می‌کند.

مهم‌ترین دستاورد فنی، جداسازی فرایند پرهزینه و ناپایدار scraping از UI است. فرانت‌اند فقط یک قرارداد دادهٔ ساده می‌شناسد و جزئیات مرورگر headless، selectorها و SQL در backend باقی می‌مانند.
